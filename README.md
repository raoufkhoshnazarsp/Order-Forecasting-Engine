| لایه | وضعیت | توضیح |
| --- | --- | --- |
| ورودی اکسل | ✅ پیاده‌شده | تشخیص خودکار ساختار، نگاشت ستون فارسی/انگلیسی، تاریخ شمسی |
| اعتبارسنجی داده | ✅ پیاده‌شده | تفکیک صفر واقعی از دادهٔ گم‌شده، سفارش‌های نگاشت‌نشده |

| Feature Engineering | ✅ پایه | تقویم شمسی، lag، rolling بدون نشت داده |
| مدل‌های Baseline | ✅ پیاده‌شده | Naive, Seasonal Naive, MA, Drift, ETS, Calendar Profile |
| پیش‌بینی AOV و GMV | ✅ پیاده‌شده | AOV جداگانه، `GMV = سفارش × AOV` برای هر روز |
| تقویم شمسی (DimDate) | ✅ پیاده‌شده | جدول ۱۸٬۱۸۴ روزه، تبدیل دقیق میلادی ↔ شمسی |

## 🚀 شروع سریع

```bash
# ۱. نصب
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# ۲. اجرای رابط کاربری
uvicorn src.serving.api:app --host 0.0.0.0 --port 8000
# سپس http://localhost:8000

# ۳. یا اجرای خط فرمان
python scripts/forecast_from_excel.py --file data/orders.xlsx --horizon 30

# ۴. ساخت قالب اکسل نمونه
python scripts/forecast_from_excel.py --template data/template.xlsx
```

## 📊 قالب دادهٔ ورودی

موتور سه ساختار را **خودکار تشخیص** می‌دهد. کافی است یکی از این برگه‌ها را در فایل داشته باشید:

### ج) مدل دادهٔ تجاری (سفارش + GMV) — سازگار با `data-model.xlsx`

| ستون | الزامی | نمونه |
| --- | --- | --- |
| `Date` | ✅ | `2026-07-01` |
| `vertical` | ✅ | `FASHION`، `Snapp-Venture` |
| `Orders` | ✅ | `3711` |
| `GMV` | ✅ | `28436156909` |
| `category` | ➖ | `ventures` (تشخیص Venture) |
| `payment_method_type` | ➖ | `INSTALLMENT`، `PAY_NOW` |
| `Active Merchants` | ➖ | `24` |

ردیف‌ها به گرید `date × entity` تجمیع می‌شوند: `Orders` و `GMV` **جمع** می‌شوند (هرگز میانگین). اگر `vertical` برابر `Snapp-Venture` باشد یا `category` برابر `ventures`، ردیف به‌عنوان یک موجودیت `VENTURE` با همان نام ثبت می‌شود.

### الف) داده‌های روزانهٔ تجمیع‌شده (توصیه‌شده)

| ستون | الزامی | نمونه |
| --- | --- | --- |
| `date` | ✅ | `2026-11-14` یا `۱۴۰۵-۰۸-۲۳` |
| `entity_id` | ✅ | `FASHION`، `V001` |
| `successful_orders` | ✅ | `420` |
| `entity_type` | ➖ | `VERTICAL` / `VENTURE` |

### ب) سفارش‌های خام (یک ردیف = یک سفارش)

| ستون | الزامی | توضیح |
| --- | --- | --- |
| `date` | ✅ | تاریخ سفارش |
| `order_id` | ✅ | برای حذف تکراری‌ها |
| `venture_id` | ✅ | شناسهٔ مرچنت/ونچر |
| `vertical` | ✅* | برای تخصیص به موجودیت |
| `status` | ➖ | فقط مقادیر موفق نگه داشته می‌شوند (`SETTLE` و معادل‌ها) |
| `merchant_type` | ➖ | `ONLINE` و غیره |
| `wallet_id` | ➖ | شناسهٔ کاربر |
| `amount` | ➖ | مبلغ به ریال |
| `voucher_discount_amount` | ➖ | تشخیص سفارش ارگانیک |
| `deleted_at` | ➖ | سفارش‌های حذف‌شده کنار گذاشته می‌شوند |
| `category` | ➖ | برای تشخیص Ventures |

**نکات مهم نگاشت ستون:**

- نام ستون‌ها **حساس به حروف نیست** و فاصله/زیرخط/نیم‌فاصله مهم نیست.
- نام‌های **فارسی** پشتیبانی می‌شوند: `تاریخ`، `تعداد سفارش`، `شناسه مرچنت`، `وضعیت` و …
- ارقام فارسی (`۱۴۰۵`) و عربی (`١٤٠٥`) به‌طور خودکار تبدیل می‌شوند.
- تاریخ شمسی (سال کمتر از ۱۷۰۰) خودکار به میلادی تبدیل می‌شود.
- ستون‌های ناشناخته نادیده گرفته می‌شوند و در گزارش کیفیت فهرست می‌شوند.

برای دیدن قالب دقیق: از دکمهٔ **«دانلود قالب اکسل»** در رابط کاربری یا `--template` در CLI استفاده کنید.

## 🖥 رابط کاربری

یک صفحهٔ فارسی و کاملاً راست‌چین با تم تیرهٔ داشبوردی (سایدبار ناوبری، پنل‌های `#1F2A40` روی بوم `#141b2d`، تأکیدهای سبز/آبی)، بدون build و بدون CDN:

- **Drag & drop** فایل اکسل با اعتبارسنجی پسوند و حجم
- انتخاب افق پیش‌بینی (۷ تا ۹۰ روز) و مدل (یا انتخاب خودکار بر اساس بک‌تست)
- کارت‌های KPI: آخرین مقدار واقعی، D+1، D+7، انتهای افق، **GMV فردا**، **AOV فردا**، تعداد موجودیت‌ها
- نمودار SVG بومی با کلید انتخاب شاخص: **سفارش / GMV / AOV** — تاریخچهٔ واقعی + مسیر پیش‌بینی + باند ۹۰٪
- جدول پیش‌بینی به تفکیک موجودیت: سفارش، GMV و AOV با مقادیر گردشدهٔ سازگار با کل
- جدول اعتبار مدل‌ها: WAPE، Bias، **پوشش تجربی بازهٔ ۹۰٪**، تعداد پنجره‌های بک‌تست و تعداد نقاط، همراه با دورهٔ آزمون
- فهرست هشدارها و برگه‌های خوانده‌شده

دسترس‌پذیری: ناوبری با کیبورد، `skip-link`، برچسب‌های ARIA، کنتراست کافی و احترام به `prefers-reduced-motion`.

### ناوبری مشترک سه صفحه

سه صفحه یک محصول‌اند، نه سه جزیره:

| مسیر | کار |
| --- | --- |
| `/` | بارگذاری، دروازهٔ کیفیت، پیش‌بینی روزانه، اعتبار مدل‌ها |
| `/comparison` | ماه‌های گذشته + سه سناریوی ماه آینده |
| `/report/` | گزارش استاتیک (دموی GitHub-Pages) |

- سایدبار از یک پارشال مشترک (`templates/_sidebar.html`) می‌آید و صفحهٔ جاری با
  `aria-current="page"` علامت می‌خورد؛ هر صفحه به دو صفحهٔ دیگر لینک مستقیم دارد.
- هر صفحه در نبود داده یک کارت راهنما («از کجا شروع کنم؟») نشان می‌دهد و پس از
  نمایش نتیجه پنهان می‌شود.
- **حافظهٔ آخرین اجرا:** هر اجرای موفق (پیش‌بینی، تحویل، مقایسه) یک خلاصهٔ
  غیرحساس در `artifacts/web_runs/last_run.json` می‌نویسد — نام فایل، مبدأ، هدف،
  افق، مدل و زمان. `GET /api/status` آن را برمی‌گرداند و هر دو صفحه نوار
  «آخرین اجرا» را بالای محتوا نشان می‌دهند، تا صفحه‌ها دربارهٔ آنچه محاسبه شده
  با هم اختلاف نداشته باشند. هیچ ردیف داده یا توکنی ذخیره نمی‌شود.

تست: `tests/test_navigation.py`

## 📊 داشبورد مقایسه‌ای (`/comparison`)

یک صفحهٔ مستقل که دو سؤال را کنار هم می‌گذارد:

1. **گذشته:** سفارش، GMV و AOV هر ورتیکال در ۳ تا ۱۲ ماه کامل گذشته، با سهم و رشد ماه‌به‌ماه.
2. **ماه آینده:** سه سناریو برای هر ورتیکال و برای `VERTICALS`.

سناریوها **دستی انتخاب نمی‌شوند**؛ از انحراف معیار خطای بک‌تست همان ورتیکال ساخته می‌شوند:

```
بدبینانه   = پیش‌بینی × (1 − 1.6449·σ)
واقع‌بینانه = پیش‌بینی
خوش‌بینانه = پیش‌بینی × (1 + 1.6449·σ)
```

`σ` نسبی است، سقف ۶۰٪ دارد، و `VERTICALS` در هر سناریو جمع همان ۷ ورتیکال است.
اگر بک‌تست کافی نباشد، هر سه سناریو برابر پیش‌بینی نقطه‌ای می‌شوند و داشبورد
برچسب «اعتبار کم» می‌گیرد — عدد ساختگی ساخته نمی‌شود.

اندپوینت: `POST /api/comparison` (نیازمند توکن کیفیت) · صفحه: `GET /comparison`
· تست: `tests/test_comparison.py`

## 📆 افق پیش‌بینی و بازهٔ دادهٔ ورودی

افق پیش‌فرض دیگر «۳۰ روز» نیست؛ از خود داده محاسبه می‌شود:

```
مبدأ  = آخرین روز موجود در فایل
هدف   = آخرین روز ماه میلادی بعد
افق   = فاصلهٔ مبدأ تا هدف   (حداکثر ۶۱ روز)
```

مثال: داده تا ۲۰۲۶-۱۰-۲۸ → هدف ۲۰۲۶-۱۱-۳۰ → افق ۳۳ روز.

| مورد | مقدار | دلیل |
| --- | --- | --- |
| حداقل مطلق | ۱۲۰ روز | دو پنجرهٔ بک‌تست ۳۰ روزه |
| **توصیه‌شده** | **۴۰۰ روز (۱۳ ماه کامل)** | پوشش چرخهٔ سالانه و چند پنجرهٔ ۶۱ روزه |
| سقف افق | ۶۱ روز | بدترین حالت: مبدأ اول ماه ۳۱ روزه |
| تاریخچهٔ کوتاه | افق به ۳۱ روز | جلوگیری از برون‌یابی بی‌پشتوانه |

افق درخواستی بزرگ‌تر از پایان ماه بعد به همان پایان ماه محدود می‌شود و دلیلش در
`plan.reason` برگردانده می‌شود. در UI گزینهٔ «تا پایان ماه میلادی بعد» پیش‌فرض است و
افق محاسبه‌شده همراه با تاریخ هدف در گزارش کیفیت داده نمایش داده می‌شود.

| بررسی | خطا (مسدود) | هشدار |

| صفرهای واقعی | — | بیش از ۱۰٪ ردیف صفر |
| پیوستگی تاریخ | شکاف > ۷ روز | شکاف > ۲ روز |
| روز ناقص پایانی | — | روز آخر < ۷۰٪ میانهٔ همان روز هفته |

## 📤 خروجی تحویل (`output.xlsx`)

علاوه بر داشبورد، یک فایل اکسل با **قالب دقیق تحویل تجاری** تولید می‌شود: یک ردیف برای هر
`تاریخ × عمودی × دسته`، برای **۳۰ روز پس از آخرین روز موجود در فایل ورودی**.

| ستون | توضیح |
| --- | --- |
| `date` | تاریخ میلادی هدف (`yyyy-mm-dd`) |
| `level` | همیشه `vertical` |
| `vertical` | یکی از `DIGITAL, FASHION, FMCG, GOLD, H&B, HOME, SERVICES, SNAPP-VENTURE, VERTICALS, SNAPP-PAY` |
| `category` | دستهٔ همان عمودی؛ برای `VERTICALS` و `SNAPP-PAY` خالی است |
| `order` | سفارش پیش‌بینی‌شده |
| `GMV` | `order × AOV` پیش‌بینی‌شده |

قواعد ساختار (دقیقاً مطابق فایل مرجع):

- `VERTICALS` جمع دقیق ردیف‌های دسته‌ای همان ۷ عمودی است — نه یک پیش‌بینی مستقل.
- `SNAPP-VENTURE` (با دستهٔ `ventures`) و `SNAPP-PAY` **هم‌سطح** `VERTICALS` هستند، نه زیرمجموعهٔ آن.
- ترتیب هر روز: دسته‌های ۷ عمودی → `SNAPP-VENTURE` → `VERTICALS` → `SNAPP-PAY` (۲۸ ردیف در روز).
- اگر منبع دادهٔ Snapp-Pay نداشته باشد، ردیف آن صفر نوشته می‌شود تا قالب کامل بماند (با هشدار صریح).

```bash
# خط فرمان
python scripts/build_delivery.py --file uploads/data-model.xlsx \
    --out outputs/forecast-30d.xlsx --horizon 30

# از طریق API (دانلود مستقیم فایل)
curl -X POST http://localhost:8000/api/delivery \
  -F "file=@uploads/data-model.xlsx" -F horizon=30 -o forecast.xlsx
```

در رابط کاربری هم دکمهٔ **«دانلود فایل تحویل»** همین خروجی را می‌سازد.

هر اجرا این مراحل را طی می‌کند و هر مرحله قابل شکست است — هیچ خطایی بی‌صدا رد نمی‌شود:

1. **خواندن اکسل** — همهٔ برگه‌ها، حذف ردیف‌های خالی
2. **تشخیص ساختار** — `raw_orders`، `daily_aggregated` یا `daily_metrics`
3. **نگاشت ستون‌ها** — فارسی/انگلیسی، ارقام فارسی، تاریخ شمسی
4. **اعتبارسنجی** — تاریخ، تعداد منفی، تکراری‌ها، وضعیت، حذف نرم
5. **تخصیص موجودیت** — `vertical` → شناسهٔ ثابت؛ Ventureها شناسهٔ عددی
6. **ساخت Data Mart** — گرید کامل روزانه با `quality_flag`
7. **اعتبارسنجی Total** — `TOTAL == Σ(leaves)` برای هر روز
8. **بک‌تست** — rolling-origin روی همهٔ مدل‌ها
9. **انتخاب مدل** — کمترین WAPE (یا مدل انتخابی کاربر)
10. **پیش‌بینی سفارش** — D+1 تا D+N برای هر Leaf
11. **تطبیق** — Bottom-Up
12. **گرد کردن** — Leafها گرد، Parentها جمع دقیق
13. **پیش‌بینی AOV** — میانگین متحرک ۱۴ روزه برای هر Leaf
14. **ساخت GMV** — `سفارش × AOV` برای هر روز و هر موجودیت
15. **اعتبارسنجی خروجی** — عدم منفی بودن، ترتیب بازه‌ها، کامل بودن افق، سازگاری GMV

## 📈 مدل‌ها و ارزیابی

**Baselineها (فاز فعال):** `naive`، `seasonal_naive` (دورهٔ ۷)، `moving_average`، `drift`، `ets` (Holt با هموارسازی ثابت).

**معیار اصلی:** `WAPE` — چون با صفرها و مقادیر کوچک پایدار است. `MAPE` معیار اصلی نیست.

```
WAPE  = Σ|Actual − Forecast| / Σ|Actual|
Bias  = Σ(Forecast − Actual) / Σ|Actual|
```

**بک‌تست:** فقط rolling-origin با پنجرهٔ گسترده‌شونده. تقسیم تصادفی train/test در هیچ نقطه‌ای از کد وجود ندارد. خروجی: `wape`/`bias` به تفکیک مدل، موجودیت و بازهٔ افق (D+1، D+1..D+7، D+8..D+30).

## 💰 پیش‌بینی AOV و GMV

GMV هرگز به‌عنوان یک سری مستقل مدل نمی‌شود. هر روز از حاصل‌ضرب دو پیش‌بینی ساخته می‌شود:

```
GMV(روز) = سفارش(روز) × AOV(روز)
```

- **سفارش** جمع‌پذیر است؛ پس مثل قبل Bottom-Up تطبیق می‌شود و `TOTAL = Σ(leaves)`.
- **AOV** یک نسبت است و جمع‌پذیر نیست. AOV هر Leaf مستقیماً پیش‌بینی می‌شود (میانگین متحرک ۱۴ روزه، چون نوسان روزانهٔ نسبت سیگنال نیست). AOV کل **میانگین وزنی** است: `Σ(GMV) / Σ(سفارش)` — نه جمع AOVهای Leaf.
- بازهٔ اطمینان GMV از حاصل‌ضرب کران‌های متناظر دو عامل ساخته می‌شود (هر دو نامنفی‌اند، پس ترتیب بازه حفظ می‌شود).
- `validate_gmv` قبل از انتشار بررسی می‌کند: GMV نامنفی، `GMV_leaf = سفارش × AOV`، و `GMV_TOTAL = Σ GMV_leaf`.

اگر فایل ستون GMV نداشته باشد، پیش‌بینی سفارش انجام می‌شود و AOV/GMV با یک هشدار صریح کنار گذاشته می‌شود.

**روز ناقص:** اگر آخرین روز فایل کمتر از ۷۰٪ میانهٔ همان روز هفته در چهار هفتهٔ قبل باشد، به‌عنوان export نیمه‌کاره از آموزش حذف می‌شود و در هشدارها گزارش می‌شود.

## 🧮 تطبیق سلسله‌مراتبی

```
TOTAL = Σ(VERTICAL) + Σ(VENTURE)
```

- **Bottom-Up** (پیش‌فرض): تضمین‌شده سازگار.
- **MinT**: تصویر پیش‌بینی‌های پایه روی زیرفضای سازگار، با سه برآوردگر کوواریانس باقی‌مانده: `ols`، `wls` (قطری) و `shrunk` (Schäfer–Strimmer).
- **Top-Down**: تخصیص پیش‌بینی کل بر اساس سهم تاریخی هر Leaf.

**مقایسهٔ روش‌ها:** `compare_methods()` خطای هر روش را جدا برای کل و برگ‌ها روی همان بک‌تست می‌سنجد و در گزارش و UI نشان می‌دهد. سهم‌های Top-Down فقط از دادهٔ پیش از اولین مبدأ آزمون محاسبه می‌شوند تا نشت نداشته باشد.

**تغییرات تاریخی سلسله‌مراتب:** `build_summing_matrix(..., as_of=...)` فقط برگ‌هایی را می‌آورد که پنجرهٔ اعتبارشان آن تاریخ را در بر می‌گیرد؛ ونچر تازه‌راه‌افتاده در گذشته ظاهر نمی‌شود.

**گرد کردن سازگار:** ابتدا Leafها گرد می‌شوند، سپس Parentها از جمع دقیق همان Leafهای گردشده ساخته می‌شوند. مجموع فرزندان همیشه دقیقاً برابر والد است.

## 🔄 Lifecycle و سناریو

**نقاط تغییر (PELT):** `src/lifecycle/changepoints.py` بدون وابستگی `ruptures`. هزینهٔ هر قطعه باقی‌ماندهٔ برازش یک خط است، نه میانگین ثابت — با هزینهٔ میانگین، یک روند تمیز به ده‌ها قطعه خرد می‌شود. جریمه از نویز خود سری مقیاس می‌گیرد، پس سری پایدار نقطهٔ تغییر نمی‌سازد. `recent_regimes(series, as_of=...)` فقط داده تا مبدأ را می‌بیند.

**ویژگی‌های رژیم:** `days_since_changepoint`، `regime_length`، `level_ratio`، `recent_shift`، `regime_volatility`.

**سناریو:** `configs/scenarios.yaml` چهار سناریو دارد (بودجه +۲۰٪، مرچنت +۱۰٪، ونچر جدید +۵۰۰ سفارش/روز، محتاطانه −۱۰٪). `apply_scenario` یک تابع خالص است: پیش‌بینی پایه تغییر نمی‌کند، والدها از جمع دقیق برگ‌ها بازساخته می‌شوند و `scenario_id` هش مشخصات آن است — پس اجرای دوباره همان عددها و همان شناسه را می‌دهد.

1. **مدل‌های ML سنگین نصب نشده‌اند.** LightGBM/MLForecast/StatsForecast در `requirements.txt` کامنت شده‌اند و باید روی سرور نصب شوند (کانتینر توسعه محدودیت حافظه دارد).
2. **بازه‌های اطمینان conformal هستند** — نیم‌عرض از باقی‌مانده‌های بک‌تست همان مدل انتخاب‌شده کالیبره می‌شود و پوشش تجربی اندازه‌گیری شده است (۰٫۸۹۹۳ برای هدف ۰٫۹۰).
3. **تصمیم‌های تعریف تارگت تأیید شده‌اند:** حذف سفارش‌های soft-deleted، فیلد تاریخ `registered_date` و حذف سفارش‌های برگشت‌خورده/ریفاند از تاریخچه (`target_v1_approved`).
4. **مسیر ClickHouse اختیاری و تأییدنشده است.** SQL موجود بر اساس سند معماری نوشته شده و روی محیط واقعی اجرا نشده؛ برای موتور فعلی لازم نیست.
5. **قاعدهٔ تشخیص Venture** (`vertical = 'Snapp-Venture'` یا `category = 'ventures'`) از سند آمده و با دادهٔ واقعی تأیید نشده است.
6. **ویژگی‌های کاربر/مرچنت/کمپین** ساخته شده‌اند اما در ورودی فعلی ستونشان نیست؛ خط لوله این را صریح گزارش می‌کند و صفر جعلی نمی‌سازد.
