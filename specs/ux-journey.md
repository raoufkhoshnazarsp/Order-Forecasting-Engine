# جریان کاربری و بازطراحی رابط

> مرجع مشترک بازطراحی رابط کاربری. هر کد (`UX-01`…) یک مسئلهٔ تأییدشده با کاربر است.
> وضعیت: `✅` انجام شد · `🟡` در حال انجام · `◻` باقی‌مانده
> آخرین به‌روزرسانی: ۲۰۲۶-۱۱-۱۶ — فاز ۰ تا ۷ (نشست اجرا، استپر، پیش‌نمایش، کیفیت، اعتبار، نتیجه، تحویل، حساسیت) انجام شد.

## ۱. تصمیم‌های تأییدشدهٔ کاربر

| تصمیم | انتخاب |
| --- | --- |
| دامنه | رابط + اندپوینت‌های نشست اجرا |
| شکل جریان | تک‌صفحه با استپر چسبان و بخش‌های تاشو |
| تم | ترکیبی: محتوای روشن با سایدبار تیره |
| مخاطب اصلی | تحلیل‌گر تجاری |
| قدم‌های الزامی | پیش‌نمایش داده، بک‌تست مستقل، داشبورد ماهانه و سه سناریو، بستهٔ تحویل، سناریوی حساسیت با فرض قابل‌تنظیم |
| ذخیرهٔ اجرا و بازگشت | بله |
| منو | گزارش استاتیک و مستندات API به «کمک» |

## ۲. جریان هدف

```
0 شروع ─ وضعیت هر قدم و «ادامه از اینجا»
1 داده ─ آپلود + پیش‌نمایش ساختار (بازه، موجودیت، برگه، نمونه ردیف)
2 کیفیت ─ ۱۰ بررسی گروه‌بندی‌شده + راهنمای رفع + پذیرش هشدار
3 تنظیم ─ افق با تاریخ هدف + مدل (خودکار پیشنهادی) + روش تطبیق
4 اعتبار ─ بک‌تست: رتبه‌بندی، «چرا این مدل»، نمودار پنجره‌ها، دانلود
5 سهم ─ محرک‌های پیش‌بینی و تغییر ساختاری
6 نتیجه ─ عدد اصلی، نمودار، جدول موجودیت سازگار با افق
7 تحویل ─ داشبورد ماهانه (هزینه‌بر/کند) · سه سناریو · سناریوی حساسیت · بستهٔ خروجی
```

قدم‌های ۱ تا ۶ ارزان‌اند و از یک نشست اجرا می‌آیند. قدم ۷ (داشبورد ماهانه) فقط با
دکمهٔ صریح ساخته می‌شود چون بک‌تست سنگین دارد.

## ۳. فهرست اصلاحات

### ساختار و جریان
- `UX-01` ✅ سه کنش هم‌زمان بی‌ترتیب → استپر با قفل/فعال/انجام‌شده
- `UX-02` ✅ تکرار آپلود و گیت در `/comparison` → همان نشست، یک آپلود
- `UX-03` ✅ نتیجهٔ یک‌جا و بی‌سطح‌بندی → خلاصه / جزئیات / فنی (بخش تاشو)
- `UX-04` ✅ راهنمای یک‌بارپنهان‌شونده → کارت وضعیت قدم‌ها که همیشه می‌ماند
- `UX-05` ✅ خروجی قبل از نتیجه فعال → «بستهٔ تحویل» بعد از سایهٔ نتیجه
- `UX-06` ✅ انتخاب مدل قبل از شواهد → مدل خودکار از بک‌تست، تغییر دستی با هشدار
- `UX-07` ✅ تغییر فایل/افق نتیجه را کهنه نمی‌کرد → برچسب «نتیجهٔ کهنه»
- `UX-08` ✅ رفرش همه‌چیز را می‌بست → نشست اجرا روی دیسک و بازیابی
- `UX-09` ✅ گزارش استاتیک در منوی اصلی → بخش «کمک»
- `UX-10` ✅ صفحهٔ وضعیت کاری نبود → قدم ۰

### داده
- `DATA-01` ✅ پیش‌نمایش ساختار بعد از آپلود (روز، بازه، موجودیت، برگه، نمونه ردیف)
- `DATA-02` ✅ برچسب چیدمان برگه بدون اصطلاح خام → توضیح فارسی
- `DATA-03` ✅ قالب/نمونه بدون توضیح → متن «کدام را انتخاب کنم»

### کیفیت
- `QC-01` ✅ «چرا مهم است» + «چطور رفع کنم» برای هر بررسی
- `QC-02` ✅ گروه‌بندی fail/warn/pass با شمارش و آیکون
- `QC-03` ✅ پذیرش صریح هشدارها با چک‌باکس
- `QC-04` ◻ خروجی ردیف‌های مشکوک (نیاز به دادهٔ ردیف در گزارش کیفیت)
- `QC-05` ✅ توضیح «صفر واقعی در برابر دادهٔ گم‌شده» در متن بررسی صفرها
- `QC-06` ✅ بن‌بست حالت fail → «بررسی دوباره» + راه رفع

### اعتبار
- `VAL-01` ✅ WAPE/Bias/پوشش با تعریف و مقیاس خوب/متوسط/ضعیف
- `VAL-02` ✅ «چرا این مدل» از رتبه‌بندی بک‌تست
- `VAL-03` ✅ جدول تطبیق با توضیح تصمیم‌محور در بخش تاشو
- `VAL-04` ✅ نمودار پیش‌بینی تاریخی در برابر واقعی برای مدل برنده

### نتیجه
- `RES-01` ✅ ستون‌های ثابت D+1/D+7/روز آخر → ستون‌ها از افق ساخته می‌شوند
- `RES-02` ✅ KPI و ستون جدول ناسازگار → یک منبع افق
- `RES-03` ✅ عدد اصلی بین ۷ کارت گم → KPI رهبر: جمع دوره و جمع GMV
- `RES-04` ✅ SVG بدون tooltip → tooltip + جدول دادهٔ جایگزین
- `RES-05` ✅ جدول ۹ ستونی → گروه‌بندی سفارش/GMV با ستون نام چسبان
- `RES-06` ✅ بخش‌های فنی قاطی → «سهم» و «جزئیات فنی» جدا
- `RES-07` ✅ فیلتر موجودیت نبود → انتخاب موجودیت روی نمودار

### خروجی
- `EXP-01` ✅ پیش‌نمایش خروجی (ردیف/ستون/نمونه)
- `EXP-02` ✅ نام فایل نامفهوم → نام تاریخ‌دار خوانا
- `EXP-03` ✅ فقط xlsx → بستهٔ تحویل با xlsx + خلاصهٔ JSON

### طراحی و دسترس‌پذیری
- `DS-01` ✅ فونت بارگذاری‌نشده → Vazirmatn در پشتهٔ فونت
- `DS-02` ✅ همهٔ کارت‌ها هم‌وزن → KPI رهبر + سلسله‌مراتب
- `DS-03` ✅ اعلام تغییر قدم و پایان اجرا با `aria-live`
- `DS-04` ◻ جابه‌جایی فوکوس بعد از خطا و پایان قدم
- `DS-05` ✅ موبایل با breakpoint واقعی
- `DS-06` ✅ متن فنی در بخش تاشو، نه جای متن کاربری

### بک‌اند
- `BE-01` ✅ هر endpoint فایل را دوباره می‌خواند → نشست اجرا (`run_id`)
- `BE-02` ✅ بدون بازگشت به نتیجه → `GET /api/runs/{id}`
- `BE-03` ✅ انبار فایل بدون چرخهٔ عمر → پاک‌سازی اجراهای قدیمی
- `BE-04` ✅ سناریوی حساسیت با فرض قابل‌تنظیم → `POST /api/runs/{id}/sensitivity`

## ۴. قرارداد API نشست اجرا

| مسیر | کار |
| --- | --- |
| `POST /api/runs` | آپلود + کیفیت + گزینه‌ها؛ فایل یک‌بار خوانده می‌شود؛ `run_id` + گزارش کیفیت + پیش‌نمایش |
| `POST /api/runs/{id}/forecast` | پیش‌بینی با توکن تأیید؛ نتیجه کامل |
| `POST /api/runs/{id}/comparison` | داشبورد ماهانه از همان فایل؛ نتیجه در نشست ذخیره می‌شود |
| `POST /api/runs/{id}/sensitivity` | سناریوی فرضی روی پیش‌بینی پایه |
| `GET /api/runs/{id}` | بازیابی نشست (بعد از رفرش) با نماهای انجام‌شده |
| `GET /api/runs` | سابقهٔ اجراها |
| `GET /api/runs/{id}/package` | بستهٔ تحویل (xlsx قابل دانلود توسط صفحهٔ جدید) |

توکن کیفیت همان قرارداد قبلی است: هش SHA-256 فایل، و بدون آن اجرا ۴۲۸ می‌دهد.
نشست در `artifacts/web_runs/<id>/` نگه داشته می‌شود و اجراهای قدیمی‌تر از سقف پاک می‌شوند.
